# 从孤立建筑到完整场景

先打开 `assets/ancient-compound.glb`，再读可编辑的 `assets/mountain-temple-layout.json`。这两个参考承担不同作用：

| 参考 | 实际内容 | 使用方法 |
| --- | --- | --- |
| `ancient-compound.glb` | 项目实际小雷音寺原创示例；13 座建筑、16 个导览点、三层院台、侧廊、山势与自然配景，26 张内嵌牌匾图 | 观察步行视角和全景中的主次体量、门—院—殿次序、边界围合、近中远景与部件完成度 |
| `mountain-temple-layout.json` | 独立参数化版本；13 座建筑、三层院台、6 组外部台阶、5 段围墙、3 块岩石 | 学习可编辑的布局、侧廊和路径组织；它不等于真实基准的全部景观几何，不能仅复制它就声称复用了全部基准细节 |

真实基准有 `landscape-ground`、`landscape-body`、`landscape-nature`、`landscape-distant` 分组。它们帮助定位要查看的场景层次；节点名不能证明自然景物数量或视觉完成度，必须打开几何观察。基准是原创游戏示意，不是官方游戏资产或文物测绘模型。

## 先诊断空旷原因

低建筑覆盖率可能来自山林、广场或水面，并不天然错误。需要判断空白中有没有用户图像展示的环境：山坡、树冠、岩壁、溪岸、院墙、廊道、远景轮廓。不能把这些全部替换为一块大地板，然后用增加主殿数量掩盖遗漏。

曾出现的黑风山布局保留了 6 座建筑，却将它们放到 96×120m 的完整地板上。其柱网占地合计约 354.5m²，约占地板 3.1%；小雷音寺参数范例约为 1918m² / 13824m²，即 13.9%。**这些是特定样例的诊断数据，不是最低合格比例。** 两者最近建筑边缘间距中位数反而接近（10.5m 和 11m），说明只看“建筑间距”会漏掉大片外围空白。黑风山没有围墙或树木声明，且建筑描述明确省略了参考中的松树；这比建筑数量更能解释森林场景的空旷。

可保留六座主体，按图像所示空间关系补充：

- **近景**：入口和转角的树干、坡石、短墙或路缘，用有变化的成组布置组织路径；主通道、门洞、台阶及摄影视线保持畅通。
- **中景**：亭子后侧的树冠、桥两端的溪岸、佛堂周围的低墙与侧廊。模型库中形制和尺度合适的亭廊、钟楼、小门可以作为辅助体量，先看预览再选，不能因为名称相似就宣称它属于目标寺庙。
- **远景**：侧后方山岩与林带形成轮廓，前后高度、尺寸、旋转和间距适度变化；避免整齐一排等大的岩石，也避免用一个巨型包围盒挡住全部道路。

三层是观察和布景方法，不要求每个小型单体任务都必须生成山林。用户要求纯建筑、白模或开敞广场时，保留这些意图并解释选择。

## 让基准和搜索真正影响结果

在 `image-analysis.md` 中增加一小段“参考迁移”：写明从真实小雷音寺 GLB 观察到什么、采用了什么、因本图不同而舍弃什么。例：“采用院门压缩—庭院展开的行走节奏；黑风山为林地，不复制雪地和对称中轴；六个地标之间用松林和溪岸连接”。不能只写“已参考示例”。

在 `sources.md` 中按具体建模决定记录检索：待确认的问题 → 实际打开的一手 URL → 资料支持的结论 → 哪个屋顶/院落/配景参数因此改变。先搜索目标建筑或其可确认的形制，再看相近类型；搜索不到精确对应时保留不确定性，不虚构尺寸或官方归属。不要把搜索仅用于 GLB 技术文档，而忽略建筑和场景信息。

可参考的实际一手资料：

- [UNESCO 苏州古典园林](https://whc.unesco.org/en/list/813/)（2026-11-05 查阅）：介绍水、石、植物、建筑的共同构景。这里只借鉴场景要素的组合，不据此把黑风山改造成江南园林。
- [上海市绿化和市容管理局：叠山造景](https://lhsr.sh.gov.cn/jnylwh/20220920/4e2c2571aa594e4ea01168364c6299a5.html)（2026-11-05 检索）：山景可与水、建筑及花木共同组织自然环境。使用于补全时标记为构景推断，不当作游戏地图的事实来源。

## 可复算的构图分析

```text
node <skill>/scripts/analyze_scene.mjs --layout <out>/layout.json --model <out>/architecture.glb --report <out>/scene-review.json
```

也可只传 `--layout` 或 `--model`。脚本自动读取技能里的真实基准、参数范例和模型库索引；任意工作目录运行，只依赖 Node.js。它输出：

- 布局柱网占地和台地投影并集、建筑边缘最近间距、外部地面高度、墙/石/树/路径/模型实例数量。
- 导览点连线每不超过 2m 采样一次，测量到建筑、墙、岩石、树冠、已知模型实例 AABB 的水平距离。距任何这些特征超过 12m 的连线段仅标记为重点检查区；12m 不是合格阈值，连线不等于实际通行路线，AABB 接近也不保证可见或构图成立。
- GLB 的 `floorBounds` 与通行范围之比单独统计；这是通行空间占比，不能拿来与布局柱网占地直接比较。整片合批景观不会以覆盖全场的 AABB 计为“已填满”。
- 实际基准节点层次、模型/贴图数量，以及布局对参数范例、GLB 对真实基准的分别比较。

`status: needs-visual-review` 是刻意保留的结果。工具不会凭比例宣布视觉通过。特别检查主路径是否持续暴露空白地板、地面是否悬浮、桥下水是否只是贴地铺装、远景是否遮住屋顶、模型库材质是否突兀。检查后在交付说明中写实际改动与仍未实现的部分。

## 合并模型后仍要验收

普通模型库条目通常没有室内通行契约。用作配景时可加保守实体碰撞；需要从门洞穿过则应建匹配的通行模型，不能将整个来源模型 AABB 当作可穿过门廊。`visualOnly` 只表示不生成碰撞，不能用来掩盖堵路的实体。增加树木时，树冠用于构图，树干用于碰撞，两者不要混淆。

完成场景后重新执行构建与 `validate_glb.mjs`，查看最终 GLB 的入口、路径转角、庭院、最高处至少四个**人眼高度**视角，另补俯瞰。模型库选择、场景分析和网络检索都不能替代最终几何、通行和目标导入器检查。
