# 悟空访古：建筑 GLB 导入规范

本说明对应当前网页导入器及 `heritageScene` 第 1 版接口。模型文件由浏览器在本机读取；导入本身不会上传文件。导入模型只在本次页面会话中保留，刷新后需要重新选择文件。

## 1. 选择适合的模型类型

| 类型 | 导入后的行为 | 需要准备什么 |
| --- | --- | --- |
| 普通建筑 GLB | 自动等比缩放、水平居中并落地；可绕行观察。整体包围盒用于碰撞，不能进入模型内部。 | 有实际网格的自包含 GLB 2.0。 |
| 可行走古建群 GLB | 保留原始米制布局，可漫游、查看导览点、俯瞰、选择单体细看和揭开屋顶。 | 网格，以及通过校验的 `extras.heritageScene` 元数据。 |

普通模型缩放后，X/Z 中较大的跨度不超过 16 米，高度不超过 8 米；按两项中较小的缩放比例处理。普通模型的墙体、门洞、台阶不会自动转为精细碰撞。

群落元数据缺失时使用普通预览；存在但不合法时直接报错，不会悄悄降级为普通预览。导览点用于显示行走指引，不会自动移动角色，也不会自动生成访古问答。

## 2. 文件和资源要求

- 使用二进制 **GLB 2.0**，不直接导入 `.gltf`、OBJ、FBX、图片、布局 JSON 或 ZIP。
- 单文件上限为 **100,663,296 字节，即 96 MiB**。等于上限可接受，超过则拒绝。
- 文件头、版本、声明总长度和首个 JSON 数据块必须有效；改扩展名不能把其他格式变成 GLB。
- `buffers` 和 `images` 必须使用内嵌二进制数据，或 `data:` URI。相对路径、本地路径和 HTTP(S) 外部资源 URI 都会被拒绝。
- 推荐普通三角网格、glTF PBR 材质，以及内嵌 PNG/JPEG 贴图。当前组件未配置 **DRACO、Meshopt、KTX2/Basis** 解码器，不要交付必须依赖这些解码器的文件。
- 导入器显示默认 glTF 场景，使用游戏自身的相机、灯光和控制器；不会播放建筑动画片段。不要依赖动画开门、移动平台或文件中的相机来实现通行。
- 文件大小通过不代表手机性能一定足够。应合并重复材质、控制网格和贴图体积，并在目标设备实际查看。

## 3. 群落坐标与节点约定

采用米制、右手坐标系、`+Y` 向上，建筑正面推荐朝 `+Z`。所有导航坐标和碰撞范围都使用群落根坐标；根与场景保持单位变换，因此这些数值也就是运行时世界坐标。

将声明放在唯一顶层根节点的 `extras.heritageScene`，加载到 Three.js 后对应 `root.userData.heritageScene`。也允许直接放在默认场景的 `extras`；整个加载场景只能出现一份声明。如果放在节点上，该节点必须是默认场景唯一的直接子节点，不能再套一个变换组。

场景和声明所在根节点不能平移、旋转或缩放。建筑子节点可以有自身变换，但元数据必须已经换算到根坐标，不能再对入口和碰撞体重复应用建筑变换。

每座建筑对应根节点的一个独立直接子节点。被 `nodeName` 或 `roofNodeNames` 引用的名称必须存在，并在加载场景中唯一；引用使用原始 glTF 节点名。屋顶节点必须位于对应建筑内部，包含网格，且不能在多个屋顶引用中重复使用。

## 4. 元数据字段

这里的“必选”意味着字段必须存在。允许空数组的字段也需要写成 `[]`；描述允许空字符串 `""`。

| 顶层字段 | 必选 | 类型与含义 |
| --- | --- | --- |
| `version` | 是 | 固定为数字 `1`。 |
| `kind` | 是 | 固定为字符串 `"compound"`。 |
| `name` | 是 | 非空群落名称，最长 160。 |
| `description` | 是 | 群落说明，允许空字符串，最长 2000。 |
| `bounds` | 是 | `{minX,maxX,minZ,maxZ}`，可行走区域。 |
| `spawn` | 是 | `[x,y,z]`，玩家出生站位。 |
| `colliders` | 是 | 碰撞盒数组；每项为 `{minX,maxX,minY,maxY,minZ,maxZ}`，允许空数组。 |
| `surfaces` | 是 | 水平地面数组；每项为 `{minX,maxX,minZ,maxZ,height}`，允许空数组。 |
| `buildings` | 是 | 建筑数组，至少 1 项，字段见下表。 |
| `walkRoute` | 是 | 导览点数组，至少 1 项；每项为 `{name,position:[x,y,z]}`。名称非空，最长 160。 |
| `cameraObstacles` | 否 | 相机避障盒数组；每项为 `{box:{min:[x,y,z],max:[x,y,z]},buildingId,roof}`。 |

未提供 `cameraObstacles` 时，导入器从玩家碰撞盒和屋顶几何范围生成相机避障。若提供，`buildingId` 必须为已有建筑 ID 或 `null`；`roof` 必须为布尔值，屋顶项不能使用 `null` 建筑 ID。空数组表示显式提供空列表，不会启用自动补全。

| `buildings[]` 字段 | 必选 | 类型与含义 |
| --- | --- | --- |
| `id` | 是 | 非空、唯一的建筑 ID，最长 100。 |
| `name` | 是 | 非空显示名称，最长 160。 |
| `description` | 是 | 建筑说明，允许空字符串，最长 2000。 |
| `nodeName` | 是 | 建筑根节点名称，最长 200；必须是群落根的直接子节点。 |
| `roofNodeNames` | 是 | 1–32 个屋顶节点名称，每个最长 200，用于单独揭顶。 |
| `entry` | 是 | `[x,y,z]`，主入口外的可站立点。 |
| `interior` | 是 | `[x,y,z]`，室内或亭内的可站立点。 |
| `sideEntries` | 是 | 其他入口站位数组，0–16 项。 |
| `floorBounds` | 是 | `{minX,maxX,minZ,maxZ}`，用于识别建筑内部；包含 `interior`。 |

其他字段不会自动变成游戏功能。接口不读取自定义脚本、远程接口地址或通用物理引擎配置。

## 5. 数量、范围与通行校验

| 项目 | 当前限制 |
| --- | --- |
| 所有坐标数值 | 有限数字，绝对值不超过 4096 米。 |
| `bounds` 的 X/Z 跨度 | 每个方向 2–256 米；所有矩形都要求 `min < max`。 |
| 建筑数量 | 1–32。 |
| 导览点数量 | 1–64。 |
| 玩家碰撞盒 | 0–4096。 |
| 水平地面矩形 | 0–4096；`height` 为 0–128 米。 |
| 相机避障盒 | 0–8192。 |
| 根节点及其后代 | 合计不超过 50,000 个节点。 |
| 寻路网格 | 0.25 米网格，总格点最多 1,050,625。 |
| 导航空间索引 | 碰撞盒与地面矩形累计估算索引量不超过 300,000。 |

地面、建筑 `floorBounds` 和所有站位必须在通行边界内。玩家碰撞盒及相机盒允许在 X/Z 边界外多出最多 4 米，但仍须与通行区域相交。建筑必须有有效几何范围，`floorBounds` 必须落在其几何的 X/Z 范围内，最多容许 0.25 米误差。

导航采用轴对齐矩形和水平地面，不会从三角网格自动生成碰撞。地面基础高度为 0；重叠地面取最高高度，因此不能表达同一 X/Z 下可分别行走的上下两层。独立技能生成可行走模型时要求建筑及墙等对象使用 90° 的整数倍朝向，以避免斜向包围盒封住门洞；普通视觉模型可使用其他朝向。

玩家高度为 1.8 米。碰撞盒需要预留人体横向间距，运行时不会再自动膨胀碰撞盒。单次地面上升最多 0.22 米、下降最多 0.26 米；技能生成器默认每级台阶不超过 0.18 米。不要把台基整体写成封闭碰撞盒，也不要用整座建筑的包围盒堵住门洞。

导入时检查以下条件：

1. 出生点、入口、室内点、侧入口和导览点均可站立，Y 值与实际导航地面高度相差不超过 0.02 米。
2. 出生点能到达每座建筑主入口。
3. 主入口与室内点双向可通行；每个侧入口与室内点也双向可通行。
4. 从出生点开始，依次到达每个导览点的路径均存在。

这些检查不能代替目视核对。模型中的墙、柱、门洞和台阶必须与元数据一致；漏写墙体碰撞仍可能导致穿墙。

## 6. 完整小型元数据示例

下面是一个四柱开放亭的完整 `heritageScene` 值，**是 JSON 元数据，不是 GLB 文件**。请将它放在真实 GLB 根节点的 `extras.heritageScene`，不要直接把这段 JSON 改名为 `.glb`。

配套网格必须包含：单位变换根节点 `courtyard-root`；它的直接子节点 `open-pavilion`；亭内名为 `open-pavilion-roof` 的屋顶网格。亭地板顶面 Y=0、范围 X/Z 为 -2.5 至 2.5；四柱位于 X/Z 的 ±2 米组合，高约 3 米；屋顶在 Y=3 米以上且与亭体分件。示例碰撞盒已为四柱预留横向余量。

```json
{
  "version": 1,
  "kind": "compound",
  "name": "四柱亭示例",
  "description": "零高差开放亭，用于说明节点、站位与导航元数据的对应关系。",
  "bounds": {"minX": -8, "maxX": 8, "minZ": -8, "maxZ": 8},
  "spawn": [0, 0, 6],
  "colliders": [
    {"minX": -2.4, "maxX": -1.6, "minY": 0, "maxY": 3, "minZ": -2.4, "maxZ": -1.6},
    {"minX": 1.6, "maxX": 2.4, "minY": 0, "maxY": 3, "minZ": -2.4, "maxZ": -1.6},
    {"minX": -2.4, "maxX": -1.6, "minY": 0, "maxY": 3, "minZ": 1.6, "maxZ": 2.4},
    {"minX": 1.6, "maxX": 2.4, "minY": 0, "maxY": 3, "minZ": 1.6, "maxZ": 2.4}
  ],
  "surfaces": [],
  "buildings": [
    {
      "id": "open-pavilion",
      "name": "四柱亭",
      "description": "开放柱廊，可由南侧走入亭内。",
      "nodeName": "open-pavilion",
      "roofNodeNames": ["open-pavilion-roof"],
      "entry": [0, 0, 3.6],
      "interior": [0, 0, 0],
      "sideEntries": [],
      "floorBounds": {"minX": -2.5, "maxX": 2.5, "minZ": -2.5, "maxZ": 2.5}
    }
  ],
  "walkRoute": [
    {"name": "亭前", "position": [0, 0, 3.6]},
    {"name": "亭内", "position": [0, 0, 0]}
  ]
}
```

## 7. 使用“图片生成古建筑 GLB”技能

下载 [技能安装包](./image-to-heritage-glb.zip)，解压后将完整的 `image-to-heritage-glb` 文件夹放入自己的 skills 目录。向 agent 提供建筑照片、游戏地图或概念图，例如：

> 使用 $image-to-heritage-glb，根据这张古建筑图片生成可导入 GLB，保留门洞与台阶，输出模型、布局参数、校验报告和预览，并验证群落通行。

技能先理解图片并记录补全假设，再按参数构造真实三维网格。它不是摄影测量，也不承诺从单张图片恢复不可见结构或真实尺寸。网页导入器本身不会把图片直接转换成 GLB。

脚本需要 **Node.js 22 或更新版本**，建模与基础校验不需要安装 npm 依赖。用实际路径替换下面的 `<skill>` 和 `<out>`；输出文件与参数文件不要使用同一个路径。

```text
node "<skill>/scripts/build_glb.mjs" --spec "<out>/layout.json" --out "<out>/architecture.glb" --report "<out>/build-report.json"
node "<skill>/scripts/validate_glb.mjs" "<out>/architecture.glb" --report "<out>/validation.json"
node "<skill>/scripts/preview.mjs" --model "<out>/architecture.glb" --port 5190
```

预览器使用固定版本 Three.js 公共 CDN，需要联网；建模与校验可离线运行。新版技能在写入 GLB 前检查完整地面边界、通行契约与参考控制器的路径连通性；报告的 `validation` 会分别列出结构、契约和路径结果。失败时不写入新模型，并将指定报告更新为 `ok:false`，避免旧成功报告误导。基础校验不是 Khronos 完整校验，也不能证明视觉网格与碰撞一致，最终仍要在本网页导入并实际走完整条路线。

安装包内的参考文件：

| 路径（相对于技能文件夹） | 用途 |
| --- | --- |
| `SKILL.md` | 技能流程与交付要求。 |
| `references/layout-schema.md` | 生成器布局参数、平台/楼梯/入口尺寸规则。 |
| `assets/example-layout.json` | 三建筑的可编辑布局参数；不是直接导入文件。 |
| `assets/mountain-temple-layout.json` | 十三建筑、三层台地的独立生成器近似模板。 |
| `assets/ancient-compound.glb` | 可直接导入的实际游戏古建群基准，含中文牌匾。 |
| `assets/baseline.json` | 基准来源、统计、SHA-256 和校验摘要。 |
| `assets/ancient-compound.glb.khronos.json` | 基准的 Khronos Validator 报告。 |

基准为“小雷音寺 · 雪山院落”：13 座建筑、16 个导览点、三层台地，文件为 21,677,252 字节。它依据用户提供的地图作原创布局解读，不是提取的官方游戏资产，也不是文物测绘复原。独立生成器模板和实际游戏基准的几何细节不同，不应宣称模板会逐面复现该基准。

## 8. 导入前后最小检查

1. 基础校验通过；有条件时再运行 Khronos glTF Validator，分别记录结果。
2. 贴图完整、中文牌匾可读；前、侧、背、俯瞰四个方向没有明显缺面或错位。
3. 在网页选择 GLB 后，确认普通预览或群落模式与预期一致。
4. 群落从出生点走到每座建筑入口和室内，走完导览路线，验证台阶、门洞、侧入口和碰撞。
5. 验证单体细看、揭顶、回漫游、返回内置群落；在手机上检查画面和操作。
6. 如需再次编辑或导入，保留 GLB、布局 JSON、生成报告及校验报告；不要只保留浏览器会话。
